Business finance dashboards.

Four Power BI dashboards for small businesses (retail, services, restaurant and a generic version), fed by an Excel spreadsheet and generated by the same code.

The problem

Selling well isn't the same as making a profit.

Many small businesses know how much they sold in a month, but not how much was left: taxes, card fees, the cost of what was sold and fixed expenses trickle out, each in a different place. How much they need to sell to break even and how much cash they'll have in 30 days are usually guesses.

Power BI Desktop is free and answers those questions, but building a model from scratch takes DAX and data modeling skills. The idea was to deliver the dashboard ready to use: you fill in an Excel spreadsheet, click Refresh and see the company's numbers.

One dashboard, four businesses

The same base, each segment's vocabulary.

The math is the same in every business, but each one talks differently. One configuration per segment changes the names, the spreadsheet columns, the color and the report's second page.

Technical decisions

Reports that come out of a script.

Building four reports by hand and keeping them identical would be a sure way for them to drift apart. So everything is generated.

Power BI in project format (PBIP)

A Node.js script writes the data model (tables, calendar, relationships and more than 40 DAX measures) and the report pages as text files. A fix made once reaches all four versions.

Validated before opening

Every report file is checked against the official schemas extracted from Power BI Desktop itself. A wrong field shows up as an error in the terminal, instead of a report that won't open.

The spreadsheet is the source

Power Query reads the Excel file through a parameter holding its path. Users only touch the spreadsheet, which is built in Python with sheets for sales, expenses, bills and goals.

Sample data that looks real

Generated with a fixed seed, from January to October 2026: seasonality, contracts that start and end, weekly delivery app payouts and customers who pay late. It comes out the same every time, which makes checking the numbers easier.

What the dashboard answers

An owner's questions, not an analyst's.

  • How much was left? Each month's income statement, from revenue to profit.
  • How much do I need to sell? The break-even point based on fixed expenses.
  • Will I run out of cash? The projected balance 30 days from now.
  • Who owes me? Overdue bills grouped by how late they are.
  • Where is the money going? Fixed and variable expenses, by category and area.
What was hard

Automating a program built for the mouse.

  1. "Blank" screens that weren't a dashboard bug. The test script clicked every refresh prompt, one per page, and fired several refreshes at once. With a single click, everything loads in under a minute.
  2. Saving with data can't be automated. Power BI opens a window with no buttons reachable by automation. The packages ship without stored data, and the guide shows the single click needed.
  3. Sharp screenshots for the guide. Capturing the window was limited to the screen size; exporting the report to PDF from Power BI itself and converting it to images gave high-resolution screenshots.
  4. Accents in PowerShell. The automation scripts must be saved as UTF-8 with BOM, or "Início" turns into garbled text.

What I learned

Good BI starts with the question.

A nice chart is the easy part. What gives the dashboard its value is picking the right questions and calculating each number the way a business owner understands it, like profit after card fees and not just revenue.

I also learned to treat reports as code: generated, versioned and validated. That's what made it possible to keep four versions consistent, fix a calculation only once and redo every screenshot in the guide without opening each screen.
