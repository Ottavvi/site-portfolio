Autenticação, chaves e CORS

Aula · 13 min

Quem é você?

APIs privadas precisam saber quem está pedindo. Os jeitos mais comuns:

  • Chave de API: um código secreto enviado num cabeçalho (x-api-key: ...). Identifica o sistema que chama.
  • Token de acesso: depois do login, o servidor devolve um token (muitas vezes um JWT) que vai em cada pedido: Authorization: Bearer eyJhbGc.... Identifica a pessoa e expira.
  • Cookie de sessão: o servidor grava um cookie HttpOnly no login e o navegador manda sozinho a cada pedido. O JavaScript nem consegue ler, o que protege contra roubo por XSS. 
const resposta = await fetch('https://api.exemplo.com/minha-conta', {
  headers: { Authorization: `Bearer ${token}` }
});

Chave secreta não vai para o front-end

Tudo o que está no JavaScript do site pode ser lido por qualquer visitante (F12 → Fontes). Uma chave paga de API colocada ali vai ser copiada. O caminho certo é um pequeno back-end intermediário: o front chama o seu servidor, e só ele, que guarda a chave numa variável de ambiente, chama a API paga.

Dica

Chaves "públicas" existem e podem ir no front, como a configuração do Firebase ou a chave do Google Maps restrita ao seu domínio. A diferença é que elas foram feitas para isso e a proteção está nas regras do servidor, não no segredo.

CORS

Por segurança, o navegador não deixa o JavaScript de site-a.com ler a resposta de api-b.com, a menos que api-b.com autorize. Essa autorização é o CORS, um cabeçalho na resposta: 

Access-Control-Allow-Origin: https://site-a.com
  • O erro "blocked by CORS policy" aparece no navegador, mas a correção é no servidor da API. Não há nada a mudar no fetch.
  • Pedidos com cabeçalhos especiais (como Authorization) ou JSON fazem o navegador mandar antes um preflight: um pedido OPTIONS perguntando se pode.
  • O CORS é uma regra do navegador. Um script em Node ou o Postman chamam a mesma API sem bloqueio nenhum, por isso não é uma proteção do servidor.
