REST: recursos, verbos e paginação

Aula · 11 min

REST é o estilo mais comum de desenhar APIs. A ideia central: a URL diz o recurso (um substantivo) e o método diz a ação. 

GET    /produtos           lista os produtos
GET    /produtos/42        um produto
POST   /produtos           cria um produto (devolve 201 e o produto criado)
PATCH  /produtos/42        altera parte do produto 42
DELETE /produtos/42        apaga (devolve 204, sem corpo)
GET    /clientes/7/pedidos os pedidos do cliente 7

Repare: nada de /criarProduto ou /apagarProduto?id=42. Os verbos ficam nos métodos.

Idempotência

Um método é idempotente quando repetir o pedido dá o mesmo efeito de fazer uma vez. GET, PUT e DELETE são: apagar o produto 42 duas vezes deixa o mesmo resultado. POST não é: dois POST criam dois pedidos. Por isso, repetir sozinho um pedido que falhou só é seguro nos idempotentes.

Listas grandes: paginação

Ninguém devolve 100 mil produtos de uma vez. A API divide em páginas:

GET /produtos?pagina=2&limite=20

{
  "dados": [ ... 20 produtos ... ],
  "pagina": 2,
  "totalDePaginas": 15
}

Outro formato comum é o cursor: a resposta traz um proximo com o endereço da página seguinte, e ele vem null na última. Funciona melhor quando os dados mudam enquanto se lê.

Erros que ajudam

Uma boa API devolve o status certo e um corpo que explica:

HTTP/1.1 422 Unprocessable Entity

{ "erro": "dados inválidos", "campos": { "email": "formato inválido" } }
Dica

Versione a API desde o começo (/v1/produtos). Quando precisar mudar algo que quebra quem já usa, crie a /v2 e mantenha a antiga por um tempo.

Teste o que aprendeu

  1. Qual rota segue o estilo REST para apagar o produto 42?

  2. Por que repetir automaticamente um POST que falhou é arriscado?

  3. Na paginação por cursor, como saber que acabou?
