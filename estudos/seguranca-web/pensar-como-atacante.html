Pensar como quem ataca

Aula · 9 min

Quase todo ataque a um site começa do mesmo jeito: alguém manda algo que o programa não esperava. Um nome com tags HTML, um campo de busca com aspas de SQL, um id de pedido que não é seu, mil tentativas de senha por minuto. Segurança, no dia a dia, é tratar toda entrada como suspeita.

A regra número 1: o navegador é do usuário

Tudo o que roda no navegador pode ser visto e mudado por quem está usando. Um campo disabled, uma validação em JavaScript, um preço num campo escondido: tudo isso se contorna em segundos pelo F12 ou chamando a API direto. A validação no front-end serve para a experiência (avisar rápido); a que vale para segurança é a do servidor.

OWASP Top 10

A OWASP, uma fundação aberta, mantém a lista dos riscos mais comuns em aplicações web. Os que mais aparecem na prática:

  • Controle de acesso quebrado: trocar /pedidos/41 por /pedidos/42 na URL e ver o pedido de outra pessoa. O servidor precisa conferir, a cada pedido, se aquele usuário pode ver aquele dado.
  • Injeção: entrada que vira código (SQL, comandos, HTML). Inclui o XSS.
  • Falhas de autenticação: senhas fracas aceitas, sem limite de tentativas, sessão que não expira.
  • Configuração insegura: mensagens de erro com detalhes internos, painel de administração aberto, senha padrão.
  • Componentes vulneráveis: dependências desatualizadas com falhas conhecidas.

Defesa em camadas

Nenhuma proteção é perfeita, então se empilham várias: validar a entrada, escapar a saída, dar a cada parte do sistema só a permissão de que precisa (menor privilégio), registrar o que acontece e manter tudo atualizado. Se uma camada falhar, a próxima segura.

Dica

Este site usa o Firebase, e a chave de configuração dele aparece no código, de propósito. Quem protege os dados são as regras de segurança no servidor (o arquivo firestore.rules), que só deixam cada pessoa ler e gravar o próprio documento. É a regra número 1 em ação.
