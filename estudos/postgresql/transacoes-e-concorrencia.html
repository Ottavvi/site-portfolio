Transações e concorrência

Aula · 14 min

BEGIN;
UPDATE contas SET saldo = saldo - 100 WHERE id = 1;
UPDATE contas SET saldo = saldo + 100 WHERE id = 2;
COMMIT;      -- ou ROLLBACK; para desfazer tudo

Uma transação é tudo ou nada (atomicidade). Se der erro no meio, nada é gravado. Fora de um BEGIN, cada comando é uma transação sozinho.

Dois usuários ao mesmo tempo

O problema clássico: duas pessoas reservam o mesmo quarto na mesma data. As duas consultam ("está livre?"), as duas veem que sim e as duas inserem. Soluções: 

-- 1) Travar a linha do quarto enquanto decide
BEGIN;
SELECT * FROM quartos WHERE id = 3 FOR UPDATE;   -- a segunda transação espera aqui
SELECT count(*) FROM reservas
 WHERE quarto_id = 3 AND status <> 'cancelada'
   AND entrada < '2026-12-26' AND saida > '2026-12-23';
-- se for 0:
INSERT INTO reservas (...) VALUES (...);
COMMIT;

-- 2) Melhor ainda: o banco proíbe a sobreposição sozinho
CREATE EXTENSION IF NOT EXISTS btree_gist;
ALTER TABLE reservas ADD CONSTRAINT sem_sobreposicao
    EXCLUDE USING gist (quarto_id WITH =, daterange(entrada, saida) WITH &&)
    WHERE (status <> 'cancelada');

A restrição de exclusão diz: não podem existir duas linhas com o mesmo quarto e períodos que se sobreponham (&&). Não importa quantas aplicações gravem ao mesmo tempo: a segunda recebe erro. O daterange(entrada, saida) inclui a entrada e exclui a saída, então quem sai no dia 24 não conflita com quem entra no dia 24.

Níveis de isolamento

O padrão do Postgres é READ COMMITTED: cada comando vê o que já foi confirmado no momento em que começa. Para regras que dependem de ler e depois escrever, BEGIN ISOLATION LEVEL SERIALIZABLE faz o banco abortar uma das transações em caso de conflito; a aplicação precisa então tentar de novo.
