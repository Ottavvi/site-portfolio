Medir e manter rápido

Aula · 10 min

Deixar um site rápido uma vez é fácil; difícil é ele continuar rápido depois de seis meses de novidades. Para isso, mede-se sempre, e de forma automática.

A aba Rede

No F12 → Rede (Network), recarregue a página com o cache desligado e com a limitação "4G lenta". Olhe:

  • O total transferido e o tempo até a página ficar pronta.
  • Os maiores arquivos (ordene pela coluna Tamanho): quase sempre são imagens ou um script grande.
  • A cascata: arquivos que só começam a baixar depois de outro terminar indicam uma cadeia que pode virar paralela (com preload ou importando antes).

Orçamento de performance

Um orçamento é um limite combinado: "a página inicial tem no máximo 500 KB e nota 90 no Lighthouse". Uma mudança que estoura o orçamento precisa compensar em outro lugar ou ser repensada. 

// ferramentas/lighthouserc.json (o deste portfólio é parecido)
{
  "ci": {
    "collect": { "staticDistDir": ".", "url": ["/index.html", "/estudos/index.html"] },
    "assert": {
      "assertions": {
        "categories:performance": ["error", { "minScore": 0.9 }],
        "categories:accessibility": ["error", { "minScore": 0.95 }],
        "categories:seo": ["error", { "minScore": 0.95 }]
      }
    }
  }
}

No GitHub Actions, a action treosh/lighthouse-ci-action roda esse arquivo a cada push e marca o commit com um X quando alguma nota cai abaixo do mínimo.

Outras ferramentas

  • PageSpeed Insights (pagespeed.web.dev): Lighthouse + os dados reais de campo, para qualquer endereço público.
  • Search Console → Core Web Vitals: quais páginas do seu site estão lentas para os visitantes de verdade.
  • web-vitals: uma biblioteca pequena para medir LCP, INP e CLS dos seus visitantes e mandar para o seu próprio painel.
Dica

Teste num celular de verdade, de preferência um modelo simples. O computador de quem desenvolve é muito mais rápido que o aparelho da maioria das pessoas que vai abrir o site.
