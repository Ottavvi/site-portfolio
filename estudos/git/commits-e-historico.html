Iniciante · Módulo 1 · Primeiros commits

Commits, diff e .gitignore

Aula · 11 min

O ciclo do dia a dia

git status              # o que mudou?
git diff                # as linhas mudadas que ainda não foram preparadas
git add index.html      # prepara um arquivo (ou: git add . para tudo)
git diff --staged       # o que vai entrar no commit
git commit -m "Adiciona o formulário de contato"

Leia o git status com calma: ele separa os arquivos em preparados, modificados e não acompanhados, e ainda sugere os comandos para mudar cada um de lugar.

Mensagens que ajudam

Daqui a seis meses, o histórico é a melhor documentação do projeto. Uma boa mensagem diz o que mudou, no imperativo, em uma linha curta:

  • Bom: Corrige o cálculo do frete para o Norte.
  • Ruim: ajustes, wip, agora vai.

Se precisar explicar o porquê, rode só git commit: abre um editor, e o texto depois de uma linha em branco vira a descrição.

Navegar no histórico

git log --oneline --graph     # histórico resumido, com os ramos desenhados
git log -p README.md          # cada mudança feita num arquivo
git show a1b2c3d              # o que um commit mudou (use o código que aparece no log)
git blame index.html          # quem mudou cada linha, e em qual commit

.gitignore

Alguns arquivos não devem ir para o histórico: dependências baixadas, arquivos gerados, senhas. Liste-os num arquivo .gitignore na raiz: 

# .gitignore
node_modules/
dist/
.env
*.log
.DS_Store
Dica

O .gitignore só vale para arquivos ainda não acompanhados. Se o .env já entrou num commit, tire-o com git rm --cached .env. E, se ele tinha uma senha, troque a senha: ela continua nos commits antigos.

Teste o que aprendeu

  1. Como ver o que vai entrar no próximo commit?

  2. Qual é a melhor mensagem de commit?

  3. O .env com uma senha já foi para um commit. Pôr no .gitignore resolve?
