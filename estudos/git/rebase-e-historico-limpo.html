Rebase, tags e um fluxo de trabalho

Aula · 13 min

Rebase

O merge junta dois ramos com um commit de merge. O rebase faz diferente: reaplica os commits do seu ramo em cima da ponta da main, como se você tivesse começado agora. O histórico fica em linha reta. 

git switch meu-ramo
git rebase main          # reaplica os commits de meu-ramo depois do último da main
# se houver conflito: resolva, git add, e git rebase --continue (ou --abort)

Muita gente configura o pull para usar rebase e evitar commits de merge à toa: git config --global pull.rebase true.

Arrumar os próprios commits antes do PR

Commits como "teste", "ajuste" e "agora vai" podem virar um só antes de abrir o pull request. O rebase interativo abre a lista dos últimos commits para você escolher o que fazer com cada um (pick manter, squash juntar ao anterior, reword mudar a mensagem, drop apagar): 

git rebase -i HEAD~3

No GitHub, o botão Squash and merge faz o mesmo na hora de juntar o PR.

Trazer um commit só

git cherry-pick a1b2c3d   # copia aquele commit para o ramo atual (útil para levar uma correção urgente)

Tags de versão

git tag -a v1.2.0 -m "Versão com a galeria"
git push origin v1.2.0
git tag                   # lista as versões

A convenção mais usada é a versão semântica: MAIOR.MENOR.CORREÇÃO. Corrigiu um erro, sobe a correção (1.2.1); adicionou algo compatível, a menor (1.3.0); quebrou algo de quem usa, a maior (2.0.0).

Um fluxo que funciona

  • A main está sempre funcionando e pode ir para o ar a qualquer momento.
  • Cada mudança nasce num ramo curto, com nome que diz o que é (corrige-frete).
  • Commits pequenos, com mensagens claras.
  • Pull request com testes automáticos antes de juntar.
Dica

Depois de um rebase num ramo que você já tinha enviado, o push normal é recusado. Use git push --force-with-lease: ele só força se ninguém mais tiver enviado nada nesse meio tempo. E nunca force na main.
