Gatilhos, condições e jobs encadeados

Aula · 12 min

Quando rodar

name: Gatilhos

on:
  push:
    branches: [main]
    paths: ['src/**', 'package.json']   # só quando estes arquivos mudarem
  pull_request:
  schedule:
    - cron: '0 9 * * 1'                 # toda segunda, 9h UTC (6h em Brasília)
  workflow_dispatch:                     # botão "Run workflow" na aba Actions

jobs:
  nada:
    runs-on: ubuntu-latest
    steps:
      - run: echo "Disparado por ${{ github.event_name }}"
  • paths evita rodar testes quando só o README mudou.
  • schedule usa a sintaxe cron: minuto, hora, dia do mês, mês, dia da semana. Sempre em UTC.
  • workflow_dispatch permite rodar na mão, pelo botão.

Expressões e contexto

Dentro de ${{ }} vão expressões com informações da execução: github.ref (a branch), github.sha (o commit), github.actor (quem disparou), secrets.NOME, env.NOME. Elas servem para montar comandos e, principalmente, para condições com if.

Jobs encadeados

Jobs diferentes rodam em paralelo, cada um na sua máquina. needs cria uma ordem: o deploy só começa se os testes passarem. 

name: Testar e publicar

on:
  push:
    branches: [main]
  pull_request:

env:
  NODE_VERSION: 22

jobs:
  testes:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: ${{ env.NODE_VERSION }}
      - run: npm ci
      - run: npm test

  publicar:
    needs: testes
    if: github.ref == 'refs/heads/main' && github.event_name == 'push'
    runs-on: ubuntu-latest
    steps:
      - run: echo "publicando ${{ github.sha }}"

O if no job publicar faz o deploy acontecer só em push na main: num pull request, os testes rodam e a publicação é pulada.

Dica

Para evitar duas execuções da mesma branch brigando (dois pushes seguidos), use concurrency: { group: deploy-${{ github.ref }}, cancel-in-progress: true }: a execução nova cancela a antiga.
