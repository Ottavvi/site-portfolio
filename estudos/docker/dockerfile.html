Dockerfile: a sua imagem

Aula · 13 min

Um Dockerfile é a receita da imagem: um passo por linha, de cima para baixo. Para uma API em Node: 

# Dockerfile
FROM node:22-slim

WORKDIR /app

# Primeiro só os arquivos de dependências, para aproveitar o cache
COPY package.json package-lock.json ./
RUN npm ci --omit=dev

# Depois o resto do código
COPY . .

ENV NODE_ENV=production
EXPOSE 3000
CMD ["node", "servidor.js"]
  • FROM: a imagem de base. As versões -slim e -alpine são menores.
  • WORKDIR: a pasta onde os próximos comandos rodam.
  • COPY: copia arquivos do seu projeto para a imagem. RUN: roda um comando durante a construção.
  • CMD: o comando que roda quando o contêiner liga. EXPOSE só documenta a porta; quem publica é o -p. 
docker build -t minha-api:1.0 .
docker run -d -p 3000:3000 --name api minha-api:1.0

Camadas e cache

Cada instrução vira uma camada, e o Docker reaproveita as camadas que não mudaram. Por isso a ordem importa: copiar o package.json e instalar as dependências antes de copiar o código faz o npm ci (lento) só rodar de novo quando as dependências mudam. Se o COPY . . viesse primeiro, qualquer mudança num arquivo refaria a instalação inteira.

.dockerignore

Como o .gitignore, diz o que não entra na imagem. Sem ele, o COPY . . leva o node_modules do seu computador, o .git e, pior, o .env com senhas: 

# .dockerignore
node_modules
.git
.env
dist
*.log
Dica

Prefira a forma em lista no CMD (["node", "servidor.js"]). Na forma de texto (CMD node servidor.js), o comando roda dentro de um shell, e o Node não recebe o aviso de desligar quando o contêiner é parado: ele demora 10 segundos e é morto à força.

Teste o que aprendeu

  1. Por que copiar o package.json e rodar npm ci antes do COPY . .?

  2. O que o EXPOSE 3000 faz?

  3. Por que o .env deve estar no .dockerignore?
