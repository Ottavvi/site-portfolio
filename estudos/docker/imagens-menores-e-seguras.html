Imagens menores e mais seguras

Aula · 13 min

Build em estágios

Para gerar um site com Vite ou compilar TypeScript, você precisa do Node e de todas as dependências de desenvolvimento. Para servir o resultado, não. O multi-stage build usa uma imagem para construir e copia só o resultado para uma imagem final enxuta: 

# Estágio 1: constrói
FROM node:22-slim AS build
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci
COPY . .
RUN npm run build

# Estágio 2: só serve os arquivos gerados
FROM nginx:1.27-alpine
COPY --from=build /app/dist /usr/share/nginx/html
EXPOSE 80

A imagem final tem uns 50 MB, em vez de quase 1 GB com o Node e o node_modules. Menos coisa dentro também significa menos falhas de segurança possíveis.

Não rode como root

Por padrão, o processo do contêiner roda como root. Se alguém explorar uma falha na sua aplicação, ganha poderes de administrador dentro do contêiner. As imagens oficiais do Node já têm um usuário comum, o node: 

FROM node:22-slim
WORKDIR /app
COPY --chown=node:node package.json package-lock.json ./
RUN npm ci --omit=dev
COPY --chown=node:node . .
USER node
CMD ["node", "servidor.js"]

Outras boas práticas

  • Versões fixas na base (node:22.11-slim) e atualização planejada, não por acaso.
  • Nada de segredos na imagem: nem em COPY, nem em ENV, nem em ARG. Qualquer um com a imagem lê com docker history. Segredos entram em tempo de execução, por variáveis de ambiente ou pelo gerenciador de segredos da hospedagem.
  • Varredura: docker scout cves minha-api:1.0 lista as vulnerabilidades conhecidas dos pacotes da imagem.
  • Um processo por contêiner: a API num, o banco noutro. Fica mais fácil escalar, atualizar e ver os logs.
Dica

docker image ls mostra o tamanho de cada imagem, e docker history minha-api:1.0 mostra o peso de cada camada: o jeito mais rápido de descobrir o que está inchando a imagem.
